Movement Tracker+ 重建分析

对原 Flutter 项目的完整拆解：它要解决什么，做了哪些功能，每块是怎么实现的，问题在哪里，以及从零重建时的设计方案。只描述行为和设计，不包含原代码。

  • 29.4k行手写 Dart
  • 119个源文件
  • 20张 SQLite 表
  • 3个测试文件
  • 2个可追踪动作

01结论

  1. 产品方向是对的。把训练记录、摄像头动作计数、饮食宏量、健康平台同步和 AI 教练放进一个 App。真正的差异点是摄像头计数，但只支持深蹲和卧推，而且每一次动作的数据算完就丢了。
  2. 功能面广，工程底子薄。没有状态管理，十来个全局单例，好几个上千行的页面，所有数据库调用都同步跑在 UI 线程上。
  3. 三个硬伤必须在重建中根除：API 密钥被打包进安装包；数据库版本号一变就删表重建（升级等于清空用户数据）；密码用无盐 SHA-256 在 UI 层哈希。
  4. 值得带走的是行为和思路。目标推荐公式（有完整单测）、计数状态机的骨架、健康同步的"只导出本 App 数据 + 删除墓碑"规则、AI 结果按天/按周缓存。
  5. 建议：继续用 Flutter 双平台，按功能分层，Riverpod + drift + 一个纯 Dart 的动作引擎包，外加一个持有密钥的轻量后端代理。平台选择需要你拍板，见第 09 节。

02项目是什么

要解决的问题

健身用户的训练、饮食和体重数据分散在好几个 App 里，MyFitnessPal、Strong、Apple Fitness 各管一块，没有一个地方能把"今天练了什么、吃了什么、离目标还差多少"放在一起看。

给出的方案

一个 App 里完成：记录训练；用手机摄像头数次数并判断动作质量；记录饮食和宏量；设定目标后自动算出每日热量和宏量；与 Apple Health / Health Connect 双向同步；AI 教练给建议、能聊天。

目标用户

普通健身人群，使用 iOS 或 Android 手机。

文档情况

没有正式需求文档。只有两份场景文档（引导 + 目标设置；首页 / 开始训练 / 记录饮食）和一份实现报告。报告称产品最初由 Spring 23 的 Group 9 设计。

Design Project 文件夹里的 CaveMap（可穿戴 LiDAR 洞穴测绘系统）是同学期的另一个项目，和这个 App 无关，重建不需要参考它。实现报告自述 44 个测试通过、1 个失败（加入 Chat 后 Tab 索引过期），本次没有重新运行。

05摄像头计数是怎么工作的

这是整个 App 最有特色的部分。用户把手机侧放拍全身侧面，App 实时识别骨架，按关节角度的变化数次数，每完成一次就判断动作是否合格。

  • 720p 视频流
  • 忙时丢帧
  • ML Kit 姿态
  • 选最佳人体
  • 每帧选置信度高的一侧
  • 算关节角
  • 5 点中位数平滑
  • 状态机
  • 只在最深一帧检查动作
  • 计次 + 反馈 + 震动
阶段进入条件备注
准备初始状态，或一次动作结束后 250 ms 冷却卧推额外要求起始姿势：躯干接近水平（±20°），手臂伸直竖起，连续 3 帧满足
下降平滑后角度连续 3 帧低于 130°动作开始时间记为这串样本的第一帧
上升角度比本次最低点回升 ≥ 8°再次跌破最低点会退回下降
完成连续 3 帧 ≥ 155°时长须在 400–5000 ms；关键点置信度 < 0.45 连续 3 帧或人体丢失则放弃本次

动作质量检查

只在每次动作最深的那一帧检查一次。深蹲：深度不够、身体前倾过多（肩到髋的水平/垂直比 > 0.60）、膝内扣（两膝间距 / 两髋间距 < 0.75）。卧推：深度不够、肘外展（肩到肘的水平/垂直比 > 1.5）。所有问题都算严重问题，合格率 = 合格次数 / 总次数，≥ 80 绿色，≥ 50 橙色。

这一块的具体缺陷

  • 深蹲深度只看膝夹角是否到 80°，提示语却说"大腿平行"。小腿正常前倾时，大腿平行对应的膝夹角只有约 60–70°，所以 80° 比平行宽松，高于平行的浅蹲也会被判合格（本报告初版把方向写反了，已更正）。更可靠的做法是直接比较髋和膝的高度。
  • App 要求侧面拍摄，但"膝内扣"要比较左右膝的水平间距。侧面视角下两膝在画面上几乎重叠，这个判断没有意义。卧推"肘外展"同理：侧面看外展体现在深度方向，而不是画面的水平方向。
  • 用处理时刻的系统时间、按"连续 3 帧"判定，结果会随手机帧率变化。
  • 每帧都可能换到另一侧且没有滞后，一次动作中途换侧会让角度跳变。
  • 单次超过 5 秒就被拒绝，慢速离心或停顿的动作不计数；最后一次之后 5 秒没动作就自动结束这组。
  • 每次的角度、问题、评分都没有保存，只把总次数带回训练页。数据库里两张姿态相关的表从来没被写入过。
  • 摄像头和检测器释放顺序有竞态：可能在推理进行中关闭检测器。录像临时文件不会被清理。

06其他核心机制

目标推荐算法

这是旧版设计最好的部分：纯函数、无副作用，并且有 7 组单元测试。

步骤规则
基础代谢19 岁及以上用 Mifflin–St Jeor：10·kg + 6.25·cm − 5·age，男 +5、女 −161、其他取中点 −78；19 岁以下用 Schofield 式公式。年龄夹在 13–100。
活动系数每周训练 1–2 次 ×1.375，3–4 次 ×1.55，5–6 次 ×1.725，7 次 ×1.9；TDEE 夹在 1400–5000 kcal。
热量调整按期限算紧迫度：≤ 42 天 1.0，≤ 84 天 0.7，更长 0.4。增肌 +TDEE×(0.06 + 0.12·紧迫度)，减脂 −TDEE×(0.08 + 0.10·紧迫度)。
热量下限男 1500，女 1200，其他 1350 kcal。
宏量蛋白质 g/kg：增肌 2.0，减脂 2.2，维持 1.8（给了体脂率就按瘦体重）。脂肪取三者最大：体重×系数、45 g、20% 热量。碳水 = 剩余热量 ÷ 4。
训练分钟按目标和"每周是否 ≥ 5 次"给出每日有氧/无氧分钟，例如减脂 30/25 或 35/30。

缺口：没有"每周减/增多少公斤"的模型，而目标编辑页又另外假设每周 0.5 kg 来估算时长，两套口径不一致；身高体重不校验；体型小的用户宏量加起来会超过热量目标；允许 13 岁用户；说明文字只有英文。

健康平台同步

  • iOS 走 HealthKit，Android 走 Health Connect，平台差异封装在接口后面，这个结构值得保留。
  • 只导出本 App 产生的数据，导入的数据不会回写，避免循环。
  • 本地删掉的导入记录会留下墓碑，不会被再次导入。
  • 游标就是"上次同步的时刻"，之后补录到更早时间的样本会漏掉。
  • 删除一餐时，会删掉该时段 30 分钟内的全部营养样本，包括其他 App 写的。
  • 本地修改过的记录不会再次导出，导出失败没有重试队列。
  • 只在打开 App、手动同步、四个页面下拉刷新时触发，没有后台同步。

AI 教练

  • 默认关闭，用户需手动开启。
  • 六种卡片共用一个系统提示：简短、用 App 语言回答、少于 100 词、不用 Markdown。
  • 用户提示由档案行（性别、身高、体重、年龄、水平）加各卡片数据拼成，六处重复。
  • 结果按"功能 + 用户 + 语言 + 日/周"缓存在一个 JSON 文件里；饮食类再加餐食指纹。手动刷新可以绕过缓存，没有上限。
  • 聊天只在第一条消息附带一次数据快照，之后数据变了也不更新；发送失败只显示一个笼统对话框。

食物搜索

  • 先搜索 USDA（每页 20 条），再批量请求详情，只为拿到份量克数。
  • 营养统一换算成每 100 g；非克数的份量（毫升、盎司）被忽略。
  • 缺失的营养素记为 0，和真正的 0 无法区分。
  • 离线时只能看"最近添加"，按关键词搜索必须联网。

启动与设置

  • 启动画面固定等待约 2.9 秒，期间什么也不加载。
  • "是否完成引导"靠"身高是否为空"来判断。
  • 设置存在一个 JSON 文件里，另有一个键绕开了设置模型直接读写。

07问题清单

  • 严重

    密钥随安装包发布.env 被声明为 Flutter asset，Gemini 和 USDA 的密钥会原样出现在 IPA/APK 里。全新克隆时这个文件缺失，构建还会直接失败。

  • 严重

    升级即清库存储的 schema 版本和代码不一致时删除全部表再重建，没有任何数据迁移。

  • 严重

    训练中途崩溃全丢训练只在点"结束"时保存，且每条插入各自独立、不在事务里，失败会留下孤儿记录，重试会产生重复。

  • 高

    密码存储不安全无盐 SHA-256，在登录页 UI 代码里计算；哈希值还随用户模型在界面间传递。

  • 高

    同步会误删他人数据删除一餐时按 30 分钟时间窗删除健康平台里的营养样本。

  • 高

    健康数据直发第三方模型体重、饮食、训练记录直接从手机发给 Gemini，只有一个开关，没有说明会发送哪些数据。

  • 高

    体重两个来源设置页改的是档案字段，首页改的是体重记录，两者可能不一致；体重历史里公斤和磅混在一起存。

  • 中

    跨页面数据过期各 Tab 一直持有启动时的用户对象，记了饮食、改了单位，其他页面要手动下拉才更新。

  • 中

    巨型页面进行中训练页 1874 行，混合计时器、HTTP、数据库、摄像头资格判断和界面；引导页和目标编辑页重复约 300 行。

  • 中

    错误被吞掉大量 catch (_) 后返回空值；用户看到的是空白卡片或异常原文。

  • 中

    性能同步 SQLite 跑在 UI 线程；饮食页每次刷新对 7 天逐日查询再逐条查食物（N+1）；首页每次改体重都重跑 8 个查询。

  • 中

    无障碍界面层没有任何语义标签，图表对读屏不可见，多处点击区域小于 44 pt。

  • 中

    测试薄弱只有 3 个测试文件；同步协调器、AI、饮食仓库、计数引擎都没有测试；.gitignore 还忽略了 /test/ 目录。

08重建设计

第 08–10 节是按 Flutter 写的初版方案，已被 Movement Tracker+ iOS 架构 取代：平台改为纯原生 iOS，AI 教练改用 Meta Muse。

原则

  1. 业务规则写成纯 Dart 并单测：目标规划、营养计算、训练会话状态机、动作计数引擎。
  2. 外部依赖全部放在接口后面：摄像头姿态、健康平台、食物库、AI、时钟、设置。测试用假实现。
  3. 数据单一来源、响应式：任何写入之后，所有页面自动更新。
  4. 迁移是一等公民：每个 schema 版本都有迁移测试，绝不清库。
  5. 客户端不放任何密钥。
  6. 从第一天起支持中英双语、深浅色和无障碍。

  • 整个动作窗口评估规则
  • 事件流
  • 动作规格是数据：视角、关节三元组、锁定角、深度目标（相对校准值）、最小幅度、停留时间、时长范围、起始姿势、规则列表（度量、比较、阈值、窗口、严重度、文案 key）。加新动作只改配置。
  • 校准：开始前站直或锁定 2 秒，记下用户自己的锁定角和肢段长度。
  • 连续评分：按深度、节奏、规则扣分算出每次分数，好/坏由分数派生。
  • 可测试：把真实训练的骨架序列录成 JSON 夹具，回放测试断言次数、被拒次数和问题。
  • 摄像头适配器：限制在约 15 fps，按"停流 → 等推理结束 → 关检测器 → 释放控制器"的顺序释放。
  • v1 动作：建议深蹲 + 俯卧撑（都适合侧面拍摄、在家就能做），卧推放到后面。

训练会话状态机

空闲→ 进行中：做组 ⇄ 休息→ 结束中→ 已完成

事件：加/删动作、加/改组、开始组、完成组（次数、来源）、摄像头结果（次数 + 每次记录）、跳过休息、结束（命名）、放弃。状态更新是领域层的纯函数，控制器在每个事件后写草稿，结束时一个事务落库。计时器由存下来的时间戳推算，App 重启也不会丢。

数据模型

  • 单一本地档案：出生日期、身高、单位、活动水平。
  • 目标：类型、每周速率、各项目标值、规划器版本，最多一个生效。
  • 身体测量：体重（kg）和体脂（%），体重只在这里存。
  • 训练：会话 → 动作条目 → 组 → 每次记录。动作目录用稳定 id 加别名。
  • 饮食：食物（每 100 g 营养可为空，多种份量，自定义归属档案，FTS 索引）→ 饮食条目。合计实时查询，不存冗余列。
  • 同步：发件箱、各数据类型的同步窗口、每次同步的运行记录。
  • 教练：洞察（类型、周期、输入哈希、提示词版本、模型）、聊天会话与消息（带发送状态）。
  • 主键用 UUIDv7；时间存 UTC + IANA 时区，local_day 写入时算好并建索引。

同步与教练

  • 导入：每种数据回读"上次窗口末尾 − 72 小时"到现在，按外部 id 幂等写入。
  • 导出：本地写入时在同一事务里写发件箱，后台按退避重试；修改会重新导出，删除按平台记录 id 删除。
  • 触发：回到前台（最短间隔 15 分钟）、手动、本地写入后去抖。
  • 教练代理只接收聚合数据（目标、今日/本周合计、趋势），返回经过校验的 JSON。
  • 按类型、周期和输入哈希缓存；每种卡片每天有调用预算；不可用时有明确状态。
  • 首次开启 AI 时显示同意页，写明哪些数据会离开手机。
