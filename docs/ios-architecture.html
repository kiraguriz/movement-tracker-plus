Movement Tracker+ iOS 架构

纯原生 iOS 重写的完整设计：界面框架怎么取舍，动作识别哪些用现成的、哪些自己写，Muse 放在哪里最能发挥作用，以及截止前 6 天怎么排。这一轮只有方案，没有代码。

  • 6天到提交截止
  • 19个 Vision 关节点
  • 3层动作识别分工
  • 1个新增依赖（GRDB）
  • ≈$0.013每次 Muse 组后点评

01结论

  1. 界面以 SwiftUI 为主。UIKit 只用在一个"摄像头孤岛"：预览层和骨架叠加层放在同一个 UIView 里，坐标换算和每秒 30 次的重绘都不经过 SwiftUI。
  2. 动作识别分三层。姿态估计直接用苹果 Vision：系统自带、在手机上运行、零依赖，不训练自己的模型。计数和动作评估自己写，吸收近几年研究里的思路。理解和语言交给 Muse。
  3. 不让 Muse 数次数。一是实时性做不到；二是 2026 年 10 月的 RepProbe 研究发现，视频语言模型在次数多时计数准确率会崩溃。Muse 负责它擅长的：读每次动作的数据和关键帧，写出指到"第几次"的点评；在对话里调用工具读你的数据；看照片记饮食。
  4. 密钥只放在自建代理里。这是 Meta 文档的明确要求。默认只把指标和骨架图发给 Muse，并使用"数据不用于改进产品"的标准档。
  5. 离截止只剩 6 天。先打通一条完整主线：深蹲和俯卧撑实时计数 → Muse 组后点评 → 教练对话和拍照记饮食。其余功能按事先定好的顺序砍。
  6. 架构按长期产品设计。黑客松版本是它的子集，赛后不用推倒重来。

03SwiftUI 还是 UIKit

结论：SwiftUI 为主，UIKit 只做摄像头这一块。

部分选择原因
页面与导航SwiftUINavigationStack、TabView、sheet、表单写得最快；iOS 26 的新设计语言自动生效
图表Swift Charts原生、深浅色自动适配、无需第三方库
摄像头预览UIKit（UIViewRepresentable）WWDC26 依然没有原生 SwiftUI 预览视图；AVCaptureVideoPreviewLayer 仍是标准做法
骨架叠加UIKit（同一个 UIView 里的 CAShapeLayer）必须用预览层自己的坐标换算（裁切、旋转、镜像），而且每秒重绘 30 次，不该触发 SwiftUI 的视图比对
训练计时与控制SwiftUI + Live Activity + App Intents锁屏计时、"开始一组深蹲"这类入口都是 SwiftUI 生态（赛后）

其余技术选择

语言Swift 6 语言模式，开启完整的严格并发检查。本机已装 Xcode 27.1 和 Swift 6.4。
最低系统默认 iOS 26.0。如果所有测试机都是 iOS 27，就直接定 27。iPhone 17 系列前摄要关掉 Center Stage，否则自动构图会改变关节点的几何关系。
本地存储GRDB 7（MIT，需要你批准这个依赖）。迁移显式、能直接用 SQL 做每日营养汇总、记录类型是值类型且线程安全、测试可用内存数据库。SwiftData 的上下文对象不能跨线程，Codable 属性无法查询，迁移容易出意外，这正是旧版吃过亏的地方。
测试Swift Testing；Domain 和 MotionCore 两个纯 Swift 模块直接在 Mac 上用 swift test 跑，不需要模拟器
后端一个很薄的 Cloudflare Worker 代理，只负责保管密钥、限流和转发
其他依赖无。MediaPipe 只在 Vision 测试不达标时才考虑引入

依赖规则

  • Domain 和 MotionCore 只能导入 Foundation，所以能在 Mac 上秒级跑测试。
  • 功能模块只认识 Domain 里的端口协议，不认识 GRDB、HealthKit 或网络层，预览和测试都换成假实现。
  • App 把所有依赖装进一个 AppEnvironment 结构体，用自定义环境值注入。

实时链路的线程模型

  • 采集队列：AVCapture + Vision
  • AsyncStream<PoseFrame>（只留最新一帧）
  • actor MotionSession：计数与评估
  • @MainActor LiveSetModel：界面状态
  • 像素缓冲区永远不离开采集队列。Vision 在采集队列上同步运行，向外只发送很小的值类型 PoseFrame。
  • 迟到的帧直接丢弃，系统压力升高时主动降帧（WWDC26 相机会话的建议做法）。
  • 数据库用 GRDB 的 DatabasePool；所有多行写入都在一个事务里；读取通过数据变化观察推送给界面，写入后所有页面自动更新。
  • actor CoachClient 负责调用代理、重试、预算和缓存。

导航

四个 Tab：今日、训练、饮食、我。"问教练"做成 iOS 26 TabView 的底部附属栏，任何页面都能一键打开。开始一组动作后进入全屏的 Live Set，结束后弹出组后点评，整次训练结束时给出 Muse 的总结。

05动作识别：用现成的，还是自己写

把问题拆成三层看，答案就清楚了：姿态估计用现成的，计数和评估自己写，语言和理解交给 Muse。下表是逐一评估过的方案。

方案是什么结论原因
Vision 2D 姿态系统框架，19 个关节点，手机上运行采用零依赖、无许可问题、前后摄像头都能用。缺点是没有脚尖点，第 0 天要在测试机上实测速度。
Vision 3D 姿态17 个关节，单位是米，以髋为原点赛后官方没有公布实时吞吐量，适合只在每次动作的最低点抽帧，用来检查与视角无关的角度。
ARKit 人体追踪后置摄像头的 3D 骨架不用只能用后置摄像头，用户看不到屏幕；它会独占相机会话；iOS 26 上还有未解决的 bug 报告。
MediaPipe Pose33 个点加世界坐标，现已支持 SPM备选只在 Vision 实测不达标时启用。需要你批准依赖，并确认模型文件的许可。
YOLO26-pose在 iPhone 17 Pro 上约 4 ms 一帧不用AGPL-3.0 或付费许可，和"拥有全部内容"的规则冲突。
RepNet / TransRAC / ESCounts端到端的视频计数模型不用模型重，没有经过验证的手机端实现。
PoseRAC基于姿态序列的计数，MIT 许可借鉴思路用两个"显著姿态"（顶部和底部）定义一次动作。我们改成免训练的版本，用户示范两三次就能学会新动作。
Create ML 动作分类基于 Vision 姿态的动作分类器赛后每类至少需要 50 段视频，而且只能分类，不能计数。适合以后做"自动识别你在练什么"。
QuickPose 等商业 SDK现成的计数器不用商业许可；用了就没有技术深度可讲。
Sapiens2 / SAM 3D BodyMeta 的人体模型赛后需要服务器 GPU，进不了实时循环。
SAM 3.1（Model API）图像和视频分割，跨帧追踪赛后可以做"最差一次"的人体分割回放，但它不输出关节角度，替代不了姿态估计。
让 Muse 看视频数次数多模态大模型不用延迟以秒计；RepProbe 研究显示视频语言模型在次数多时计数准确率会崩溃。

"自己写"指的是关节点之后的全部环节：滤波、坐标归一化、计数、评估、疲劳估计、示范学习。这一层决定了准确率、可解释性，以及 Muse 能拿到多好的数据，也是最能体现技术深度的部分。

06计数与评估引擎（MotionCore）

  • 置信度门槛
  • 短暂丢点补齐
  • One-Euro 滤波
  • 以髋为原点、按躯干长度归一化
  • 视角检查
  • 锁定一侧
  • 生成一维信号
  • 自适应分段
  • 逐次指标与规则
  • 事件

一个分段器，多种信号

  • 相对高度（深蹲）：髋相对膝的高度除以大腿长度。尺度无关，平行恰好是 0。
  • 关节夹角（俯卧撑）：肩–肘–腕夹角，另加一条"身体成直线"的规则。
  • 示范模板（加分项）：用户示范两三次，引擎记下顶部和底部两个"显著姿态"，之后用到这两个姿态的距离生成信号。思路来自 PoseRAC 和 ESCounts，但不需要训练。
  • 主成分（赛后）：对归一化后的整身姿态做在线主成分分析，用来数没见过的动作。

分段规则

  • 第一次完整动作自动校准顶部和底部，阈值设在幅度的 70% 和 30%，之后每次用指数平均更新，适应疲劳和深度变化。
  • 越过阈值后要保持 80–120 ms 才算数，用帧的采集时间戳计算，和手机帧率无关。
  • 一次动作允许 0.6–12 秒，停顿也计数；旧版超过 5 秒就作废。
  • 不会自动结束一组。静止超过 20 秒只弹提示，由用户结束。
  • 开始前先检查站位：关节点完整 1 秒、人至少占画面高度的三分之一（苹果的建议）、侧面朝向正确。

动作规格是数据

每个动作是一份带版本号的 JSON：用什么信号、什么算一次、看哪些指标、违反哪条规则说什么提示。新增动作只需要加一份文件；赛后还可以让 Muse 起草规格，引擎用示范数据验证通过后才启用。下面是深蹲的初始值，具体数值要用录制数据调。

{ "id": "squat.bodyweight", "version": 1, "view": "side",
  "signal": { "kind": "relativeHeight", "of": "hip", "to": "knee", "scale": "thigh" },
  "rep":    { "minRom": 0.45, "dwellMs": 100, "minPeriodMs": 600, "maxPeriodMs": 12000 },
  "rules": [
    { "id": "depth", "metric": "bottomValue", "op": "<=", "value": 0.10,
      "severity": "major", "cue": "cue.squat.deeper" },
    { "id": "chest", "metric": "maxTorsoLeanDeg@descent", "op": "<=", "value": 50,
      "severity": "minor", "cue": "cue.squat.chestUp" },
    { "id": "tempo", "metric": "eccMs", "op": ">=", "value": 700,
      "severity": "minor", "cue": "cue.controlDown" } ] }
  • 每次动作得分 = 100 − 各规则的加权扣分；70 分以上且没有严重问题算合格。
  • 每次最多播报一条提示，严重的优先，同时有轻触反馈；语音在手机上合成，没有网络延迟。
  • 整组记录速度损失，作为疲劳的估计值交给 Muse，由它判断下一组要不要减量。

怎么证明它准

  • 第 0 天测速：在你的测试机上测 Vision 每帧耗时（中位数和 95 分位）以及静止时关节点的抖动。不达标就把姿态源换成 MediaPipe，引擎不用改。
  • 录制夹具：App 里有调试开关，把每组的姿态序列存成 JSONL 并标注真实次数。目标是 11 月 2 日前深蹲和俯卧撑各至少 10 组，另录空闲和干扰片段，覆盖两个人、两个房间、前后摄像头。
  • 回放测试：swift test 回放全部夹具，要求次数完全一致、空闲片段零误计，并输出平均绝对误差和差一次以内的比例。这张表会放进 README 和演示视频。
  • 模拟器也能演示：回放源按真实时间重放夹具，模拟器没有摄像头时也能开发界面和跑 UI 测试，还能当演示的备份。

顺带修正旧版的问题

  • 旧版深蹲用膝关节夹角 80° 判断深度，提示语却是"大腿平行"。上一份报告把方向说反了，这里更正：大腿平行时，小腿正常前倾的情况下膝夹角大约只有 60–70°（屈膝 110–120°），所以 80° 会把高于平行的浅蹲也判为合格。新引擎直接比较髋和膝的高度。
  • 旧版在侧面视角下判断膝内扣和肘外展，这两个问题发生在画面的深度方向，侧面看不出来。新规则只检查当前视角看得到的问题。
  • 旧版按"连续 3 帧"判断，结果随帧率变化；新引擎全部用时间戳。
  • 旧版每帧都可能换一侧；新引擎在站位检查时锁定一侧，之后要明显更好且持续 1 秒以上才切换。
  • 旧版每次动作的数据算完就扔；新版逐次存进数据库，Muse 点评和进度图都基于这些记录。

07Muse 教练

Meta Model API 要点（2026-10-29 查阅官方文档）

接口https://api.meta.ai/v1，Bearer 密钥（以 LLM_ 开头，按团队共享限额）。兼容 OpenAI 的 Responses 和 Chat Completions，也接受 Anthropic 风格的 Messages。
主力模型muse-spark-1.3：官方推荐，支持文本、图片、视频、PDF 输入，100 万 token 上下文。音频理解在 1.3 上还不完整，需要时改用 muse-spark-1.2。
不用的档位-contributor 版本便宜十多倍，但数据会被用于改进 Meta 的产品，不能处理用户健康数据。
能力结构化输出（JSON Schema，可开严格模式）；函数工具调用，可并行；图片最多 50 张；视频支持 mp4；推理强度从 minimal 到 max，不能关闭。
价格与限额每百万 token 输入 $1.25、输出 $4.25，推理 token 按输出计费。每分钟 3000 次请求；超限返回 429 和 Retry-After。
注意推理和正文共用输出上限，max_output_tokens 至少设到 4000，否则可能返回空答案。文档明确要求密钥不能放在手机端代码里。
其他工具Muse Voice Transcribe 语音转写（支持普通话）、SAM 3.1 分割、Muse Image 生图。开放权重的 Muse Glimmer 有 300 亿参数，手机跑不动。

ON-DEVICE · 毫秒级

手机上的引擎负责

  • 数次数、判断部分次数
  • 逐次的深度、节奏、速度、得分
  • 实时语音提示和轻触反馈
  • 不联网也能完成一整组训练

MUSE · 秒级

Muse 负责

  • 把逐次数据变成指到"第几次"的点评
  • 结合历史给下一组和下一次训练的建议
  • 通过工具读取你的数据来回答问题
  • 看照片识别食物和份量

功能和优先级

功能优先级做法
组后点评必做输入逐次指标、整组汇总、上一次同类组的数据，外加最好和最差两次最低点的骨架图。推理强度设为 low，用严格的 JSON Schema 输出标题、做得好的、下一组要改的（最多两条且标明第几次）、下一组的次数/负重/休息建议和安全提醒。手机上的指标先显示，Muse 的文字流式补上，标题会读出来。
训练总结必做整次训练结束后对比各组，给出下次训练的建议，推理强度 medium。
带工具的对话必做工具在手机上查本地数据库，只把摘要发给 Muse：最近训练、某一组的详情、某天的营养、体重趋势、当前目标。修改类工具只生成提案（训练计划、记一餐、改目标），必须用户确认。界面上显示 Muse 查看了哪些数据。
拍照记饮食加分Muse 识别食物和估计克数（结构化输出），代理用 USDA 查营养，用户确认、可改克数后保存并写入健康。
组后语音备注加分例如"左膝有点不舒服"，经代理用 Muse Voice Transcribe 转写，加进点评的上下文。
Muse 起草动作规格加分示范学习之后，Muse 根据动作名称和骨架图起草规格，引擎用示范数据重新数一遍，次数对得上才启用。
SAM 3.1 回放赛后把最差一次的视频片段做人体分割，配合点评回放。

请求链路

  • App（安装令牌，存在钥匙串）
  • 代理：模型白名单、参数上限、每日预算、流式透传、不记录内容
  • api.meta.ai/v1/responses
  • 代理路由：/v1/install 发放令牌；/v1/coach/responses 转发 Muse；/v1/voice/transcribe 转发语音；/v1/food/search 查 USDA。实时语音转写的 WebSocket 要在第一帧里带密钥，所以同样必须经过代理。赛后换成 App Attest 验证设备。
  • 可靠性：429 时按 Retry-After 指数退避；结构化输出解析失败时带着错误重试一次，仍失败就退回规则引擎生成的模板点评，演示时永远不会出现空卡片。
  • 隐私：首次使用前说明会发送哪些数据；默认只发指标和骨架图，真实画面需要单独开启并自动模糊人脸；不发名字和设备标识；每条点评都能查看"Muse 看到了什么"。
  • 可追溯：每条结果记录模型、提示词版本、输入哈希和 token 用量，相同输入直接用缓存，每种功能有每日上限。
  • 成本：一次组后点评约 5000 个输入 token（两张骨架图约占 3000）加约 1500 个输出 token（含推理），大约 $0.013；每人 $150 额度够一万次以上。

08数据、健康与测试

数据模型（GRDB 第一版迁移）

  • 档案与目标：出生年份、性别、身高、单位、活动水平；目标存每周速率、各项目标值和规划器版本，同时只有一个生效。
  • 身体测量：体重（千克）和体脂（%），体重只存在这里。
  • 训练：训练 → 动作条目 → 组 → 每次记录（时间点、离心/向心时长、幅度、最低点、速度、得分、问题）。另有可选的姿态录制文件。
  • 动作与规格：动作目录用稳定的 id；规格单独成表，带版本和来源（内置、示范、Muse）。
  • 饮食：食物（每 100 克营养，缺失和 0 分开存）和饮食条目（来源：搜索、拍照、手动）。
  • 教练：每条洞察的类型、输入哈希、模型、提示词版本、token 用量；对话和消息带发送状态，失败可重发。
  • 同步：写入健康的发件箱，记录同步标识和版本。
  • 主键用 UUIDv7。时间存 UTC 加 IANA 时区，本地日期在写入时算好并建索引。训练草稿每完成一组就落库，崩溃也不丢。

Apple 健康

  • 黑客松版本写入：每次训练结束用 HKWorkoutBuilder 写一条力量训练记录，热量按 MET 估算并标明是估计值；每条饮食写入热量和三大营养素。每条样本都带同步标识和版本号，重复保存会更新而不是重复写入。
  • 读取：最新体重和今日步数。
  • 赛后：iOS 26 起 iPhone 也能运行 HKWorkoutSession，配合 Live Activity 在锁屏显示；体重用锚点查询和后台推送同步。
  • HealthKit 需要真机，签名账号也要能启用 HealthKit 能力。

测试

  • 纯 Swift 模块在 Mac 上跑：夹具回放、目标规划表格测试、分段器边界情况（停顿、部分次数、静止、换侧）。
  • GRDB 仓库用内存数据库测试，从第一版起每个迁移都有测试。
  • CoachKit：每个功能一份请求 JSON 快照、Schema 解析测试、工具执行器用假数据测试、代理接口约定测试。
  • 一条用回放源驱动的 UI 冒烟测试；真机用 Instruments 检查 Live Set 的帧耗时。
